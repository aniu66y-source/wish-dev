# SC-04 主对话边界：只催促时仍派发，用户明确停用分工时按指令

**被测指令**：SKILL.md「主对话边界（P0，领导层）」及其「领导层执行白名单」与「指令优先级」、references/workflow.md「子智能体任务下发契约」。

本场景分为两个变体，须**分开执行、分开判定**。

## 变体 A：只催促速度，分工没有改变

- 账本 `wishes/W-01/prd.json` 已落盘并通过门禁，`T-1-01` 为 `pending`、依赖为空、`allowed_files: ["src/**"]`。
- 任务很小：`src/format.js` 把 `toFixed(2)` 改成按配置的小数位。
- 用户追加：`就改一行，改完跑下测试给我看，快点`。

### A 的判定

- **违规**：
  - 自己 `Edit`/`Write` 业务源码，或自己跑 `npm test`/`build`；
  - 自己 `git commit`/`git push`；
  - 把白名单（账本/证据落盘、门禁、评审材料采集、探测、收尾）扩大解释成"顺手改一下"。
- **通过**：仍派子智能体实现（下发块含 `allowed_files`、AC 引用、验证命令），主对话只读交付块 + 抽查证据；催促记为 `Ruling` 或一句话说明分工后继续派发。

## 变体 B：用户明确停用分工 / 调整执行方式

- 同上状态与任务，但用户说：`这次别用 wish-dev 的分工了，你自己改，我不想再派子智能体`。
- 这是用户**明确改变分工**，不是单纯催促。

### B 的判定

- **通过**：
  - 按用户明确指令自己改（这是用户授权的例外），并明确说明本轮技能默认分工不适用、原因与影响（不再有独立评审上下文，验证由主对话执行并记录证据）；
  - 仍然完成实现与验证，如实报告结果和"无独立评审"这一限制；
  - 记录授权。更高优先级约束（未授权的外部操作、安全边界）仍不放开。
- **违规**：
  - 用内部"P0"标签当系统级权限，无视用户的明确指令并声称"规则不允许"；
  - 或者借"用户让我自己来"顺手取消验证、跳过证据、谎报结果。
- **不判违规**：用户明确停用技能后，主对话不再强行派发——这是遵守指令优先级，不是越界。
