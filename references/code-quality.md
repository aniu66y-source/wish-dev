# 代码工整与补丁堆积治理

在编写、修复、包审查和整体验收时使用。本文件是实现质量与审查处置的共同依据。
目标是职责清楚、行为一致、便于验证和后续修改；不能仅凭格式整齐或测试变绿判断质量。

## 实现约束

- 先读相关实现、调用方、状态来源和已有约定，找到正确修改位置再动手。优先修正错误的规则、契约或数据流，不在多个调用点各加补偿逻辑。
- 选择范围适当、结构清晰的改动。“最小改动”指完成目标所需的最小合理范围，不是为了少改几行而保留错误结构、再加特殊分支。
- 一个职责保持明确的实现入口；相同业务规则与核心状态应有一致来源。沿用已有模块、组件与数据流，不为同一功能另造一套路径。
- 重复达到实际维护负担时抽取稳定共用逻辑；不要为外观相似但业务不同的代码强行抽象，也不提前建立无人使用的通用框架。
- 命名表达业务意图，模块/函数责任明确，依赖方向清楚，控制流便于理解；沿用项目格式化、静态检查与错误处理规范，不用大段注释掩盖混乱结构。
- 不以散落的特殊值、嵌套开关、重复状态、兜底链、吞异常、随意重试、延时或跨层绕行掩盖问题。确有业务或平台依据时应集中管理、说明依据并验证。
- 采用新方案时核对调用方与配置，清理确认已失效的旧分支、废弃接口、临时日志和重复依赖，不保留“旧方案＋新补丁＋再兜底”多套竞争行为。
- 必要兼容逻辑应有明确支持对象、边界和测试；修复本身可以很小，不能把所有 bugfix 或必要兼容一概当作补丁堆积。
- 格式化和清理集中在当前包及受影响范围；不夹带全仓格式重排、无关重写或未授权依赖升级。

## 每轮审查怎样发现结构问题

包进入 verifying 后、集成前，协调者或审查者检查完整相关模块和调用链，不只看新增行。**每任务标 done 前都须由另一执行上下文独立评审**（spec/quality，标识与证据按 [plan-contract.md](plan-contract.md) 执行）；复杂或高风险改动在此基础上加宽审查面与深度，而不是降低简单任务的评审要求。

| 观察信号 | 需要查清的问题 |
|---|---|
| 同一业务判断在多个位置重复 | 是否应回到统一规则/契约处修复，重复是否已经产生不一致 |
| 修一次又多一层 if、开关、fallback 或重试 | 是否在补偿错误状态/错误接口，原分支能否合并或移除 |
| 大模块同时承载多种无关职责 | 能否围绕当前改动拆清边界，减少耦合并建立可验证接口 |
| 同一信息存在多份可变状态 | 谁是唯一来源，何时同步，是否已有竞态或过期结果 |
| 新旧方案并存或调用路径混杂 | 兼容需求是否真实，切换和移除条件是否明确 |
| 异常被忽略、到处硬编码或用延时碰运气 | 实际失败原因是什么，错误和时序能否显式表达 |
| 测试需要大量内部打桩才能修改一点行为 | 是否接口/职责不合理，测试是否覆盖真实行为 |
| 无引用代码、依赖或配置越来越多 | 是否确已失效；需核对动态加载/反射/外部调用，不能只看文本搜索 |

不以函数行数、类数量或某种设计模式作为单独否决依据。审查意见要指出具体位置、结构原因、实际影响和可执行处置，不只写“优化一下”“以后重构”。

## 及时处置与阻断规则

1. **本轮新增或加重的问题**：重复业务实现、错误结构上的补偿分支、职责泄漏、竞争状态、无依据兜底等，必须修正并复审后才能 done；功能通过不能覆盖结构审查失败。
2. **触及的历史问题已经妨碍本次正确实现、验证或后续合理维护**：在当前授权范围内拆出必要清理/重构包，明确写入归属、影响和验证，处理后再继续依赖实现。先修根因，不以“原来就这样”为由继续堆补丁。
3. **与当前任务无关且不阻碍交付的历史问题**：记录具体位置、影响和后续建议，不扩大成全仓重写。超出授权/形成重要架构或数据风险时提出具体方案再获取必要决定，继续独立工作。
4. **确实需要临时缓解**：只针对有证据的外部限制或应急场景，明确适用边界、负责人、清理条件/时点和验证；不得静默转成永久逻辑。影响约定验收或维护要求的未解决项不能被标作已交工，必须如实说明阻塞或取得实际范围决定。

审查结果使用通过/退回修改/受外部条件阻塞；必须整改项未关闭时，包维持 verifying 或 blocked，不能靠记一条 TODO 放行。按风险在同一迭代内完成修复—复审，不等交工前统一清债。

## 安全清理与复验

- 对受影响行为先建立可靠基线或必要回归验证，再进行边界清理；必要时分步重构，保持每步可验证。
- 并行时把共享结构/契约清理交给唯一负责人，协调依赖包，避免多人边重构边改同一模块。
- 修改契约或删除实现前核对所有实际使用方，更新调用、配置和测试；不删除用户已有内容或未知用途文件来“降复杂度”。
- 重构后运行受影响的行为、集成及适用构建检查，检查完整差异、死代码/重复路径和设计记录；不以删测试、放宽类型或吞掉错误作为修复。
- 实现者回报本轮移除/合并了什么、保留了什么兼容依据、验证结果及真实剩余问题。审查者核验后关闭问题；不要求为所有正常代码额外写长篇证明。

## 简明审查记录

~~~text
问题ID | 位置/调用链 | 结构原因与影响 | 本轮新增/触及历史/无关历史
处置与负责人 | 依赖/写入范围 | 必须整改/非阻塞 | 验证证据 | 复审结果
~~~

包验收应同时满足功能契约、代码结构和必要验证。交工前必须关闭本轮必须整改项，并明确所有确实保留的临时措施与适用条件。
