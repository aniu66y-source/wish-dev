# 从需求到交工的阶段执行依据

本文件供协调者选择当前阶段的动作和完成证据。先看用户约束、现有项目和交付目标；步骤可合并与迭代。阶段产物可以是同一份项目记录里的章节，不以文档数量判断完成。明显不适用的环节记录原因；用户明确要求的功能或发布不得自行标不适用。

## 阶段裁剪判定

1（需求）与 12（交工）恒做；中间阶段按交付物类型裁剪，目的是不为小任务强走满 12 阶段。裁剪=明显不适用，不=跳过用户明确要求的环节。

| 任务类型 | 可裁剪阶段 | 判定依据（记录原因时照此写） |
|---|---|---|
| 单模块、可回退的 bug 修复 | 4、5、6、7 | 沿用现有栈与结构，无新选型、无界面/数据/架构变更、复用现有工程 |
| 文案、配置、依赖版本升级 | 5、6、7 | 无交互、数据或结构变化 |
| 纯后端 / API / 无状态工具 | 5 | 无图形界面，以命令或 API 使用体验替代 UI |
| 有界面的新功能 | 无（5、6、7 必做） | 涉及用户路径、共享契约与工程 |
| 有状态、多用户服务 | 无（6 的并发/负载均衡必评） | 共享写入、一致性、容量需实际判断 |
| 明确要求上线或部署 | 10、11 必做，不得降级本地 | 交付层级含目标环境 |

裁剪规则：

- 只在“明显不适用且不影响用户明确要求”时裁剪；拿不准就保留该阶段。
- 部署条件与成本在第 4/6 阶段调查，避免开发结束才发现无法交付。
- 每个裁剪项记入账本（progress.md 或 prd.json 草稿）：`阶段 | 不适用原因 | 触发重新评估的条件`。

## 1. 需求获取与澄清

- 获取要解决的问题、目标用户、主要场景、成功表现和交付目标，保留原始表达。
- 从附件、原型和项目调查补齐平台、范围、数据、集成、预算/时间及部署条件；不预设一定是 Web 产品或一定需要购买服务器。
- 仅对无法调查的核心业务歧义集中提问，给出推荐选择和实际影响；已有足够信息即推进。

完成依据：能描述“谁在什么场景完成什么事、交付在哪里、怎样验收”，并区分事实、假设、硬约束及关键待决事项。

## 2. 现状调查与可行性评估

- 现有项目先读取规则、代码结构、Git 状态、已有改动、依赖版本、启动及检查方式、运行环境和已知失败。
- 新项目先调查可复用资源、现有账号/服务/设备和接口条件，选择最简单可交付的路径。
- 对不确定能力做有界验证，区分文档描述、配置/文件存在与实际运行证据。版本、费用、服务能力等易变信息核实官方来源；无依据时明确不确定。
- 产品实现前按 [research-and-architecture.md](research-and-architecture.md) 调研同类 GitHub 实现，保留实际 SHA、实现链路和取舍；已有适用证据可复用，不把 README 或本技能流程示例当产品调研。
- 识别目标环境的资源、网络、兼容、数据和权限限制；阻塞项尽早暴露。

完成依据：有可行路径和证据边界，了解基线与关键依赖，不靠猜测进入大规模实现。

## 3. 产品方案与验收定义

- 整理核心流程、功能范围和优先级、用户角色与权限、输入输出、业务校验及异常分支。
- 适用时定义数据生命周期、重复提交/重试、审计和第三方失败时的行为，避免把错误处理留到最后。
- 用 AC 编号定义可观察结果，同时定义运行、部署和交接等交付验收；区分原型、模拟数据和真实业务。
- 对新增愿望记录变更及其设计、依赖、成本、验收影响，不能只改代码而保留旧基线。

完成依据：每个必须功能和交付目标都能对应验证方法，不需要用户替开发者补全常规技术细节。

## 4. 技术选型与成本评估

- 优先沿用符合需求的现有技术栈和工具。对影响交付的重要选择比较少量可行方案，说明推荐理由、兼容性、维护与迁移代价。
- 按需求选择前后端/应用框架、存储、认证、通信和部署方式，不为小工具引入不必要服务。
- 核对版本兼容、依赖维护和使用条件。说明部署所需资源、一次性/持续费用以及依赖的账号和凭据；无法估算时指出缺失信息。
- 常规技术选择自主决定并记录；超出已授权费用、平台边界或形成重要业务取舍时才询问。

完成依据：选型与需求/环境一致，重要取舍有依据，用户无需预先提供技术方案；没有把“可免费试用”当长期无成本。

## 5. UE／交互与 UI 设计

有界面时实施；无图形界面则记录不适用，并定义适用的命令/API 使用体验。

- 先梳理信息架构、页面/导航、用户任务路径和关键操作，再确定页面布局与视觉。必要时制作线框或可交互原型验证流程。
- 沿用品牌、原型和设计系统；没有既定规范时自主建立适合产品的色彩、字体、间距、组件和反馈规则，不把每个视觉细节都交用户决定。
- 覆盖正常、空白、加载、成功、失败、无权限和危险操作确认状态；处理表单校验、防重复操作、焦点与键盘路径等实际可用性。
- 按指定平台/视口验证布局和密度。用户限定桌面或固定尺寸时忠实执行，不擅自扩大移动端范围；要求多端时再验证相应适配。
- 用户流程与数据契约保持一致。标明模拟交互；在真实渲染表面检查布局、溢出、状态与核心操作，修正偏差。

完成依据：关键用户路径和交互状态有可执行设计，必要原型/页面可查看；UI 完成不只意味着画面存在。

## 6. 系统架构与数据设计

- 划定模块/服务职责、前后端与第三方边界、调用方式、接口输入输出、错误协议和兼容要求。
- 按实际数据需求设计模型、约束、状态流转及必要并发/幂等处理，明确唯一数据来源与模拟边界。
- 涉及身份或敏感数据时确定认证、授权、信任边界及秘密配置方式，日志不得泄露密钥或不必要的敏感内容。
- 涉及既有数据时设计兼容与迁移顺序；区分应用回退和数据恢复，不假设代码回退能撤销数据变化。
- 针对实际风险规划性能、资源和观测方式，避免无依据地微服务化或过度设计。
- 实现前明确运行时并发、共享状态、资源过载和负载均衡；不适用写原因及扩容触发条件。容量结论必须来自实际测量，开发代理并行不代表产品并发能力。

完成依据：实现包所需的共享契约和负责人明确，UI 与服务可以按同一业务/数据模型开发。

## 7. 工程搭建与交付计划

- 建立或复用工程结构、开发/测试/生产配置约定、必要依赖、环境变量示例、代码规范和运行命令；不把真实密钥写进仓库。
- 验证最小工程能够启动并通过适用的基线检查，明确构建/测试方法；CI/CD 复用已有方案，需要新建时按规模实施，不以建立某平台流水线为强制前提。
- 建立需求到工作包/验收的追踪关系、依赖图、文件归属与动态调度策略。不预设包数或并发数，按项目规模、依赖、耦合、风险及实际运行资源选择并行或串行。部署准备、测试及交接也纳入计划。
- 先交付可运行的最小纵向链路，再迭代补齐，尽早发现前后端、数据与部署差异。

完成依据：工程可运行，包可领取，依赖和验收明确，已考虑最终发布方式。

## 8. 分包并行开发

- 由主对话（领导层）派发的子智能体多线并行承担产品补充、设计、架构、前端、后端、测试和部署等实际需要的角色；角色是职责，不硬编码代理名。
- 稳定接口后并行开发不重叠模块。跨包契约变更先通知协调者，更新契约和受影响包再继续；不能各自猜接口。
- 统一管理共享文件、锁文件和迁移。每轮集成可演示的完整业务增量，不把全部联调留到最后。
- 实现遵循 [code-quality.md](code-quality.md)：修正根因和统一实现，避免重复状态、局部补偿分支与旧方案堆叠；必要结构清理纳入包和依赖，不与其他写入任务互相覆盖。
- 每包返回实际交付、验证和证据；缺真实服务/硬件时明确模拟范围并保留待验证项。

完成依据：相关工作包可集成并达到包验收，未完成依赖/后台任务没有被隐藏。

## 9. 集成、评审与质量验证

- 按实际风险执行静态/类型检查、相关单元和集成测试、构建及完整用户路径。
- 核心流程覆盖数据保存/读取、失败反馈、角色权限和外部集成等适用行为。UI 检查真实操作与状态，不能只凭截图；API 测试不能替代完整前端路径。
- 复杂或高风险实现由独立上下文评审差异及证据；必要时检查安全、性能、可用性、平台兼容和数据恢复。
- 每轮按 [code-quality.md](code-quality.md) 检查完整相关模块、调用链及补丁堆积；本轮引入/加重或妨碍当前实现的结构问题及时修复或安排必要重构，复审后才集成。不能以功能通过或记 TODO 替代整改。
- 记录环境、版本、命令、结果和证据。失败定位根因、修复并重跑；原有失败单独说明，不降低检查或验收要求。
- 所有必需项必须实际执行；不适用须有理由，不能借此取消用户要求。

完成依据：集成版本满足当前验收，必须整改的功能与结构问题已闭环并复审，剩余限制明确。构建成功不代替业务验收，也不代替维护性审查。

## 10. 部署准备与发布

按需读取 [release-handover.md](release-handover.md)。仅交付本地程序时，此阶段负责目标机器的安装/分发、配置与启动验证；要求上线时须执行实际目标环境发布。

- 调查目标、账号权限、资源与网络条件，形成具体构建、配置、迁移、备份、健康检查和回退步骤。
- 对不可逆迁移和可能影响现有服务的动作说明具体影响、保护和恢复方式，核对授权。已有明确的发布授权不重复询问。
- 构建可识别的产物并在目标环境发布，避免把未授权开发文件或凭据打包。

完成依据：目标环境实际运行预期版本，部署记录与配置/数据处理有证据；退出码 0 只是发布过程的一部分。

## 11. 上线验收与运行观察

- 在实际入口/目标设备验证关键业务、身份与权限、数据行为和所需外部连接。
- 检查启动状态、健康状态、必要日志/指标；对异步任务、重启后行为或资源限制按实际风险验证。
- 做有界首轮观察，发现发布引入问题及时修复或按批准方案回退。保护生产数据，不用真实用户数据随意做破坏性测试。
- 首轮观察结束后交接维护方式；未约定长期值守时不承诺持续监控。

完成依据：实际部署结果通过验收，已知运行限制和观测方式已交代；测试环境通过不能代替明确要求的生产验证。

## 12. 交工与维护交接

- 交付对应版本的源码、适用运行产物、真实运行入口、使用说明、配置变量清单、验证记录及剩余限制。
- 适用时提供部署/更新、备份恢复、回退和故障定位方式，交代服务/域名/证书等维护归属及成本依赖；不交付明文密钥。
- 对照最初交付目标与全部必须验收项核对，区分技术交工、待用户签收和因外部条件受阻。
- 用户要求人工签收时提供证据等待真实确认，不伪造确认；没有此要求时不额外制造签字流程。

完成依据：接收者能按说明使用和维护交付物，全部约定目标有证据。缺失关键真实联调、发布授权或目标环境时只能如实交付已完成部分。
