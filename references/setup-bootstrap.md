# 执行环境就绪检测与补齐

本技能仅在 Windows 运行；开发任务启动前，先只读检测宿主的**执行能力**是否就绪。本文件提供检测项、缺失判定与补齐规则。

使用前提：宿主为**支持工具调用（tool calling）的 agent 软件**，且**能派生出拥有独立执行上下文的执行体**（子智能体，或满足等价条件的隔离子任务）；当前模型支持工具调用。不满足任一则不能声称完整开发，降级为整理需求/计划。

补齐策略（缺失才补，不覆盖已有）：

自动补齐仍受项目规则与实际授权限制；需要提权、影响全局环境或新增费用时核对授权，不能把本节当作绕过宿主审批的许可。

- Node ≥ 18 检测不到时**直接安装/补齐，不停**（运行时常规依赖，check-plan.mjs 门禁依赖；SKILL 启动检测对 Node 按本节自动补齐，宿主能力缺失与敏感凭据仍交用户）。
- 已授权、目标明确的项目级非敏感配置缺失时直接补齐；非敏感不等于自动获得修改权限，具体边界见下方配置规则。
- 缺少敏感凭据时交用户通过宿主支持的安全机制设置；示例变量名不含真实值。涉及全局默认、账号、付费选择或未知端点且缺授权时，先补齐必要决定，不影响其他独立工作。
- 不覆盖用户既有配置/数据；不通过跳过权限或关闭沙箱扩大权限。

## 检测项

依次只读检查，记录每一项的就绪状态；不满足的按「缺失补齐」规则处理，不停下等待：

| 检测项 | 检测方式 | 就绪标志 |
|---|---|---|
| 1. 宿主可派生独立执行体 | 宿主工具索引中存在可派生执行体（子智能体 / 隔离 subtask 或宿主等价能力），并按「能执行工具、上下文隔离、任务可追踪、可独立评审」四项核对 | 四项均可核实 |
| 2. 模型支持工具调用 | 当前宿主/模型可发起工具调用 | 可发起（实检一次只读工具） |
| 3. Node ≥ 18 | `node --version` | 版本号 ≥ 18（check-plan.mjs 门禁依赖） |

**无等价执行体 = 无法用本技能执行**：主对话的分派、验收、独立评审都依赖它。判定按能力而非名称——普通函数调用、共享上下文的步骤或只是名字叫 subtask 的封装不算等价；四项都满足的隔离子任务按等价处理，并在账本记判定依据。此项不满足即记 `blocker`，不开工（只能降级为整理需求/计划）。

任一项不满足时，记录具体缺失项和影响范围，按「缺失补齐」处理；补齐后复测，仍失败才记入风险/阻塞。

## 开工硬门控

本技能靠宿主子智能体**多线并行**提高交付效率：

- 第 1 项（可派生等价执行体）**是硬前提，不可降级跳过**：没有独立执行体就没有可分包并行的执行者。
- 第 2、3 项须实检 PASS（工具调用可用、Node ≥ 18）。
- PASS 以**实际复测输出**为准（可派生、工具 schema、node 版本号），不以手填 ok 或"装过就算好"判定。
- 第 1 项不满足 → 记 `blocker` + 恢复条件，不开工，可先做不依赖执行体的独立调查/设计（但不得启动分包开发）。
- 第 3 项不满足（Node < 18）→ 按「缺失补齐」装 Node，装不通记 `blocker`。

## 模型/凭据配置（适用时）

模型凭据与版本以实际探测为准，不写死 provider/model。宿主已有可用模型/认证时沿用，不覆盖、不重配。

- 端点、provider 结构、模型名须有实际配置或官方说明作为依据；仅在已授权、目标明确的项目级范围内自动补缺。改变全局默认、账号、付费选择或使用未知端点前核对影响与授权，已有明确授权不重复询问。
- 凭据引用使用目标宿主实际支持的环境变量或秘密管理语法，不把 `{env:VAR}` 当成通用语法；先核对 schema，不能凭示例生成会被当作字面值的配置。
- **需要真实 API key 值而安全凭据入口尚未配置时**，告知用户需设哪个变量（如 `MYPROV_API_KEY`），由用户在环境变量配置；不在配置、脚本或仓库写明文密钥。变量缺失记入 `risks`，不阻断其他独立工作。

## 缺失补齐

| 缺失项 | 补齐动作 | 是否停下 |
|---|---|---|
| Node < 18 或缺失 | 直接安装 Node ≥ 18（官方包管理器/官方安装方式），装后 `node --version` 复测 | 不停，自动 |
| 模型凭据未设（环境变量缺失） | 停下，告知需设哪个变量，由用户配置；记入 `risks`，不阻断其他独立工作 | 暂停依赖该凭据的工作 |
| 宿主不可派生等价执行体 | 无法自动补齐（宿主能力）；记 `blocker` + 恢复条件，交用户处理 | **blocker，不开工** |
| 子智能体可派生但派发失败（工具被拒/额度） | 按实际原因定位根因；属宿主硬限制时记 `blocker`，不伪装、不绕过 | 视根因 |

补齐后必须**重新检测并实检通过**（以实际输出/复测为准）才允许进入开发流程；任何一项未通过即视为环境未就绪。

## 自动补齐的安全边界

自动补齐**不得**：通过跳过权限或关闭沙箱扩大权限；覆盖用户既有配置、数据或凭据；安装与开发目标无关的软件；为通过门禁手填 `ok`。安装仅用官方包管理器/官方安装方式，安装后必须实际复测对应项，不以安装命令退出码 0 当通过。

**补齐失败不得硬闯**：权限不足、网络不可用、包不存在等导致失败，记录 `blocker` + `resume-condition`，如实说明缺项，不假装该项已通过、不静默跳过门禁；可继续不依赖该项的独立工作。权限/网络类失败交用户处理，不通过伪装客户端或绕过权限强行继续。

## 未决缺口入账本

检测发现的缺口不得静默假设，按 [workflow.md](workflow.md) 账本字段记录，衔接 `prd.json` 与 `progress.md`：

| 缺口性质 | 记入 | 写法 |
|---|---|---|
| 暂不阻断、按假设推进 | `assumptions` | 假设内容 + 影响 + 复核条件 |
| 已自动补齐但需复核（Node 装完待复测、凭据变量未设） | `risks` | 触发条件 + 影响 + 处置/恢复 |
| 阻断开发（宿主不可派生等价执行体、核心业务/目标无法代行） | `blocker` + `resume-condition` | 最小缺项 + 消除阻塞所需证据/授权 |

缺口补齐或消除后更新对应账本条目并复核，不保留已失效记录。

## 检测通过

全部检测项实检 PASS（含经补齐后复测达成）时：

- 记录检测时间、各层版本/能力快照（不写死版本号，以实际输出为准）。
- 原生即 PASS 的项不必重复探测；经补齐达成的项，本轮复测即为其检测。
- 宿主可派生独立执行体：主对话直接派发任务执行，不套远程服务，不递归调用本技能。

## 平台前提

本技能的**使用前提是宿主支持工具调用且能派生独立执行体（子智能体或等价隔离子任务）**；不满足任一则只能整理需求/计划，不声称完整开发。安装命令、配置字段、版本选择、provider/model 名称均不在此写死，以实际探测结果与上游官方文档为准；密钥始终走环境变量。本机运行根与移植说明见 [portability.md](portability.md)。
